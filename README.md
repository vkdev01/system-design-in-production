# System Design in Production

**A build-it-yourself manual for the nineteen systems that show up in every senior
system-design loop, reconstructed from the engineering write-ups that the people
who actually ran them published.**

Read it as a site: **https://vkdev01.github.io/system-design-in-production/**

Nine production write-ups plus four AI-systems chapters are the spine of this repo:

| # | The interview question | The write-up it comes from |
|---|---|---|
| 01 | Design a chat app | How Discord Stores Trillions of Messages |
| 02 | Your Postgres database is full. Now what? | Herding elephants: sharding Postgres at Notion |
| 03 | Scale a database without rewriting the app | How Figma's databases team lived to tell the scale |
| 04 | Design a payment API | Designing robust and predictable APIs with idempotency (Stripe) |
| 05 | How do you stop a user getting charged twice? | Avoiding Double Payments in a Distributed Payments System (Airbnb) |
| 06 | Design a rate limiter | Scaling your API with rate limiters (Stripe) |
| 07 | Design Slack | Real-time Messaging (Slack Engineering) |
| 08 | Design driver matching for Uber | H3: Uber's hexagonal spatial index |
| 09 | Design a notification system | How Discord handles push request bursts of over a million per minute |
| 10 | Serve a 70B model at 100 req/s | Efficient Memory Management for LLM Serving with PagedAttention (SOSP '23) |
| 11 | Answer questions over 10M docs with citations | Introducing Contextual Retrieval (Anthropic) |
| 12 | An agent that survives a pod restart | Building effective agents (Anthropic) + chapters 04/05 |
| 13 | Ship a model change safely | Two-proportion testing, calibrated judges, slices |

Each chapter follows the same nine-step path: the problem and the naive design, the numbers
that decide it, the mental model, the annotated flow chart, a sizing pass (per-component
capacity, bytes on the wire, benchmark targets), the algorithm end to end (request
walkthrough, pseudocode, invariants, edge cases), the build from scratch to a working
prototype, the production layer (Kubernetes manifests, AWS managed services, limits, failure
drills), and finally the two-minute interview answer.

## Why this exists

Diagrams teach you the boxes. Write-ups teach you why the boxes broke. This repo
takes the write-ups and adds the part they leave out: the code, the configs, the
capacity math, and the operational drills, so you can run the thing and watch it
fail in a controlled way.

## Run the site locally

The site is generated by `site_builder/build.py` — a small Python generator with
its own templates, stylesheet and scripts. No docs framework, no theme package.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python site_builder/build.py --serve    # http://127.0.0.1:8000
python site_builder/build.py            # writes dist/

# GitHub Pages serves this as a project page, so production needs the prefix:
SITE_BASE=/system-design-in-production python site_builder/build.py
```

The visual system is ported from
[engineering-notes](https://github.com/vkdev01/engineering-notes) — the same
Manrope + JetBrains Mono pairing, 17.5px/1.75 body, 300px numbered sidebar with
filter and in-page section list, 800px reading measure, `.ann` callouts, `.code`
cards with a language head, and the seven light colour schemes (violet, navy,
moss, cobalt, rose, bronze, wine) switched by `data-theme` and remembered in
localStorage. Fonts are self-hosted; Mermaid is vendored, so nothing loads from a
third-party CDN at runtime.

## Repo layout

```
docs/           the manual, as markdown (the only content source)
  foundations/  mental models, capacity numbers, the 9-step method
  chapters/     the nineteen chapters
  appendices/   k8s + AWS pattern library, drills, sources
site_builder/   build.py, Jinja templates, stylesheet, scripts, vendored mermaid
code/           runnable prototypes, one directory per chapter
deploy/         Kubernetes manifests, Terraform modules, compose files
dist/           build output (generated, not committed)
```

## Publishing the site

The site is built by `.github/workflows/deploy.yml` and published with GitHub
Actions. Pages must be switched on once for the repository (already done):

1. Repository **Settings → Pages**
2. **Build and deployment → Source: GitHub Actions**
3. Re-run the **Deploy site** workflow (Actions tab → Deploy site → Re-run jobs),
   or push any commit.

The published URL is `https://vkdev01.github.io/system-design-in-production/`.
`mkdocs build --strict` is the gate CI uses; it must pass before a deploy runs.
